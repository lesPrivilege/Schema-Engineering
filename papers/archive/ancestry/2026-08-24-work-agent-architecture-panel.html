Work Agent 架构判断

产品不再管理对话，而是管理持续存在的工作语义。

Courtwork 的起点不是“做一个法律 Agent”，而是追问：上一代垂类 AI 产品留下了什么不会折旧的资产？实践把答案一路推到 Extension、Work Contract、Human Review、Matter 与无感连续性。

01旧产品

Chatbot + 场景功能；产品壳易被通用 Agent 吸收。

02残留资产

专业 Provider 对任务、来源、字段、风险与完成方式的判断。

03重新封装

把专业判断从独立产品中剥离，变成通用 Work Agent 可加载的 Extension。

04架构发现

Extension 最终不是 prompt 包，而是模型、人和系统共同消费的持续工作协议。

真正的产品主线：旧产品考古 → Extension → Validation Layer → Contract → Matter。

开场讲法：先说明法律只是第一块试验田。我的问题不是市场上还缺不缺一个合同 Chatbot，而是当通用 Agent 可以执行工作以后，上一代垂类软件积累的专业判断应该以什么形态留下。

先分离产品形态与专业判断

被吸收的是垂类壳；值得回收的是已经筛选过的工作知识。

法律计算器、合同审查、商业分析等声明式功能未必形成长期护城河，但它们证明了一些工作面已经被反复筛选，能够标准化、配置化并交付。产品考古的任务，是把这些判断从旧壳中剥离。

FORM FACTOR / 易折旧

独立垂类产品

  • 行业 Chatbot 壳
  • 场景菜单与快捷入口
  • 大段 system prompt
  • 单用途 workflow 页面
→
WORK KNOWLEDGE / 可迁移

Extension 中的专业声明

  • 什么工作值得标准化
  • 需要哪些输入与权威来源
  • 哪些判断必须显式呈现
  • 什么才算完成与可交付

不是否定旧 Provider，而是回收它们已经付费标注过的专业工作面。

展开：这一步解释为什么 Courtwork 最早被构想为 Extension，而不是法律 SaaS。产品形态可能被更强 Agent 一网打尽，但专业场景的选择、字段和验收并不会自动从模型里长出来。

Coding Agent 与 Work Agent 的结构差异

工作场景缺的不是又一个 prompt，而是一层可检查的中间状态。

Coding 成熟不只因为训练数据多。计算机环境机器可读，编译、类型检查、测试和 build 又提供了廉价反馈。一般工作知识分散，错误常常是语义性的：文件成功生成，不等于工作正确完成。

CODING AGENT

环境天然可执行、可反馈

  • 代码、文档、接口与错误信息机器可读
  • 编译、lint、测试、build 能低成本回报失败
  • Agent 可以自行修改并重新验证
WORK AGENT

语义知识分散、完成难以自证

  • 行业知识散落在 Provider 与企业内部
  • 合同不报错，不代表风险已经识别完整
  • 报告生成成功，不代表抓住真正问题

精确边界：Work Contract 不是 compiler，不能证明 correctness；它提供的是 validation layer——把开放任务收缩成可检查、可追溯、可由人复核的中间状态。

防守点：不要把“工作契约是编译器”讲得过满。更严谨的说法是，它补上工作场景缺失的 validation layer：不能证明语义正确，但能让来源、覆盖、结构、权限与人工裁决变得可见。

Schema Engineering

Work Contract 把“帮我审合同”编译成一组可执行、可复核的责任。

它不是更长的 prompt，而是一份结构化场景声明。模型不再临场重新发明方法，而是在已经声明好的工作空间中检索、推理、引用并填写结构化对象。

STAGES
工作阶段
材料进入、模板对比、外部核验、风险判断、人工裁决、成果交付。
INPUT
来源声明
原合同、标准模板、法规库、主体库与企业私有知识。
PROVENANCE
证据与坐标
判断注明引用源、原文位置；原始文件保持只读。
SCHEMA
结构化中间态
风险、理由、严重度、修订建议、证据与覆盖状态。
VALIDATOR
确定性检查
必填字段、格式、引用完整性与脚本可校验部分。
DECISION
人类裁决
逐条接受、修改或驳回；高风险判断不由模型自批。
TERMINAL
完成与交付
风险已复核、选择已落定、正式成果可以写回或导出。

开放式语言任务被压缩为：模型可写、系统可验、人可读改签。

讲法：这页落到 Courtwork 实物逻辑。先对比标准模板，再接法规、主体与内部知识；原文件只读；每条判断带来源和位置；结构与引用走脚本门；专业风险最终逐条交给人。

实践后的抽象升级

同一份 Schema 同时面对模型、人和长期任务。

最初只是想约束 Agent，真正实现后却发现：这份契约同时成为 execution contract、review interface 与 semantic state。它因此不再只是提示词工程，而是产品的共享协议。

Model-facing

Execution Contract

把开放式任务收进有限结构。轻量模型不用自己涌现完整工作方法，只需检索、推理并填充声明对象。

Human-facing

Review Interface

用户逐条看到判断、证据和原文位置，再接受、修改或驳回；HITL 落在工作对象，而不是聊天确认。

Task-facing

Semantic State

已经填好的结构记录“知道什么、判断到哪里、依据是什么、还有什么没完成”，可以直接承担续行语义。

风险判断→Evidence→原文坐标→接受 / 修改 / 驳回→状态更新

传统 Chatbot 交付一段答案；专业 Work Agent 交付一个可以裁决的工作面。

追问：如果面试官问 Schema 为什么不是大 Prompt，就用三面协议回答。Prompt 只解释模型输入；这里还定义人怎样 review，以及任务如何跨天、跨调用维持一份高密度状态。

从 Conversation Management 退出

Session 是 chronology；Matter 才是 semantics。

对话标题只是历史摘要，无法稳定代表案件、项目、角色关系或工作进度。Conversation log 应继续保存，但退回系统资源；产品的一等对象改为 Matter——持续存在、可恢复、可交付的事项。

INFRASTRUCTURE LEAK

User → Session → Messages

  • 用户自己新建和命名对话
  • 靠标题猜“那件事”在哪一条
  • 恢复时重放或压缩 chronology
  • 工作状态隐藏在自然语言历史中
→
PRODUCT OBJECT

User → Matter → Semantic State

  • 用户只需继续这件事
  • Contract 与当前状态默认恢复
  • 原始 history 与 evidence 按需读取
  • Chat 只是 Matter 的交互记录
Matter
├─Contract / Schema角色、工作规则、输入输出与裁决协议
├─Semantic State当前已经知道、决定和等待的事情
├─Resources文件、证据、外部知识与业务对象
├─Interaction Log完整 chronology，可追溯但不默认重放
├─Tools / Authority可观察、可执行和必须确认的边界
└─Extension为这一类 Matter 加载的领域能力包

不做 Session 管理，不是少一个侧栏；是把模型基础设施概念从用户对象中拿走。

讲法：用户想说的是“继续刚才那件事”，不是“恢复 8 月 17 日某个标题的 Session”。这页把交互设计和系统架构接起来：Conversation 仍存在，但不再承担业务对象和长期状态。

Context Hierarchy

连续性不建立在越来越长的对话上，而建立在显式语义状态上。

连续交互时可以利用 Provider cache；隔几天恢复时，优先加载稳定契约与当前结构化状态。原始消息、文件和证据完整保留，但只在需要时检索，避免 summary 反复压缩造成语义漂移。

L1Contract / Stable State

最小、最稳定、默认注入：工作规则、角色属性、长期关系约束。

Always
L2Current Semantic State

事项现在到哪里：已识别对象、当前判断、用户裁决、未完成步骤。

Current
L3Raw History / Evidence

完整消息、原文件、历史事件和引用材料；建立索引，由模型按需回溯。

Retrieve
恢复顺序：Working semantic state 常驻 → evidence 可追溯 → raw history 渐进式展开。

高质量工作状态自然承担 Memory；不需要先造一个“记忆产品”，再寻找它应该记什么。

边界：这里不是不保存历史，而是不把 chronology 当成主要 context。连续 summary 是有损黑盒，长期还可能累积漂移；显式状态则可以被 UI、校验器和人共同检查。

Matter Schema 的一般化

普通 Chat、专业 Worker 与陪伴角色，可以是同一对象模型的不同配置。

当相同机制既能表达合同审查，也能表达普通对话和角色关系，最上层抽象便不只叫 Work Contract。它更接近 Matter Schema：声明模型是谁、什么状态值得保存、允许做什么、人与系统在哪里介入。

普通 ChatMINIMAL CONTRACTWeb Search 等少量工具临时资源 + 后台高价值状态
专业 WorkerWORK CONTRACT检索、文件、知识库与业务工具结构化判断 + evidence + review 状态
陪伴角色ROLE CONTRACT少量安全工具稳定人格 + 关系状态 + 重要事件
Persona 也不只是 prompt：stable role contract + relationship state + salient events + retrievable history。

Chat 不是另一套系统；它可以是一个没有加载专业 Extension、工具权限很少的 Matter。

展开：陪伴角色这个例子证明 Work Contract 只是更一般抽象的一个 subtype。用户隔两个月回来，系统先恢复稳定角色和关系，再按需 recall 事件，不需要把几十万 token 重新塞进 context。

Agent complexity should be absorbed by the product

技术对象不等于用户心智对象。

Prompt、Context Window、Session、Memory、MCP、Tools、Permissions、Compaction 和 Handoff 可以是开发者产品的控制面；对普通专业工作者，它们意味着产品把 harness 直接泄漏给了用户。

Agent / Harness Concepts

  • Session 与 Conversation Branch
  • Prompt、Context 与 Compaction
  • Memory Entry 与 Retrieval
  • Tools、Permissions 与 Extension
→

User Mental Model

  • 案件、合同、条款与证据
  • 角色、关系和过去发生的事情
  • 风险、确认、修改与交付
  • 一个 Composer：继续说就可以

成熟的 Work Agent 产品，不教普通用户管理 Agent；它替用户静默做好 context、memory、权限和续行。

面试句：我不认为普通用户应该学习怎么管理 Agent。下游产品的价值不是和强用户的 code / low-code 工具竞争，而是做功能取舍、防呆和领域翻译，让用户只看到自己的工作。

HITL 与防呆不是零碎功能

产品替用户决定机器权限，只把有业务语义的裁决交给人。

如果普通用户不应该成为 Agent engineer，权限配置责任就必须由产品承担。原件只读、不可永久删除、Trash 可恢复、高风险动作确认、结果经 review 提交，共同构成默认安全结构。

机器操作语义write_file?

由产品默认值、作用域与可恢复机制吸收，不反复打扰用户。

系统安全语义read-only / trash / provenance

原件不覆盖、删除可恢复、每次修改与来源都有记录。

业务决策语义接受这一条修改？

人只对真正需要承担后果的内容作出接受、修改或驳回。

只读观察→准备工作件→人工裁决→有限写回→可恢复记录

好的 HITL 不问用户是否允许一次 tool call；它问用户是否接受一项业务后果。

讲法：防呆不是“权限系统做得很全”，更可能是把 27 个技术权限选项删掉。产品先替用户决定安全默认，只把具有业务语义、不可逆或需要专业责任的选择暴露给人。

模型更强以后，什么仍然存在

Contract 的两部分折旧速度不同；架构应该允许其中一部分消失。

SOTA 模型可能不需要被详细教导合同审查常识，但模型再强，人仍要 review，企业仍要 provenance，权限仍要边界，状态仍要持久化。把两部分拆开，才能避免用静态 workflow 抵抗能力进步。

MODEL-FACING

Intelligence Scaffolding

  • 告诉模型应该关注什么
  • 把任务拆成更细步骤
  • 为轻量或本地模型补充工作语义
  • 随模型能力增长可以逐渐变薄
HUMAN / SYSTEM-FACING

Interaction & Verification Protocol

  • 结果怎样结构化与持久化
  • 证据、原文与来源放在哪里
  • 谁能批准动作、怎样 review
  • 失败、恢复、写回和交付怎样发生
预制 UI 的意义：稳定工作只有有限的高频交互原语；复用 review 界面，是缓存后的产品知识，不是落后的 workflow。

真正耐久的不是“教模型怎么想”，而是工作对象、状态、证据、权限和人与 Agent 的交互协议。

防守点：面对“模型更强后 Schema 会不会没用”，不要回答不会。承认 model-facing scaffolding 会折旧，并让它可替换；真正稳定的是 human/system-facing contract。

从 Courtwork 推出的通用产品论

六条判断，共用一套架构。

这条推理可以同时回答：为什么不是 Chatbot、怎样设计 Memory、为什么需要 HITL、普通用户为什么难用 Agent，以及模型继续变强后产品还剩下什么。

01Matter，而不是 Session，是一等产品对象。
02Contract，而不是 Conversation，是长期连续性的主要载体。
03History 应该完整可追溯，但只在需要时进入 Context。
04Extension 把领域判断编译成模型、人和系统共同消费的协议。
05Agent complexity 应由产品吸收，而不是要求普通用户学习 harness。
06Scaffolding 可以折旧；state、provenance、permission 与 human interface 不会自动消失。
从 Session 管理退出，才能让产品真正开始管理工作、关系与责任。
